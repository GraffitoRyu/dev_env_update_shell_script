# 다른 Mac에 pnpm 정책 적용하기

이 문서는 각 Mac에서 담당 에이전트가 진단하고, 사용자가 실제 변경을 승인한 뒤 적용하는 절차다. 저장소의 코드 변경 승인만으로 다른 Mac의 패키지나 셸 설정까지 변경하지 않는다.

## 적용 정책

- 승인된 pnpm 메이저는 `pnpm-policy.zsh`의 `PNPM_MAJOR` 하나로 관리한다. 현재 값은 `11`이며, 그 계열 안에서 Homebrew가 제공하는 최신 버전을 사용한다.
- Node.js는 기존 `update.sh`의 Node.js 24 LTS 설치·활성화 방식을 유지한다.
- `migrate-pnpm.zsh`는 최초 설치와 셸 전환을 맡는다. 기본 실행은 진단이고, `--apply`를 지정해야 변경한다.
- 전환 후 `update.sh`는 자동 실행에서도 목표 pnpm formula를 개별 갱신한다. 수동 전체 Homebrew 업그레이드에서는 pnpm 계열을 제외하여 승인하지 않은 메이저로 전환하지 않는다.
- 기존 npm pnpm, Corepack, 일반 Homebrew pnpm 설치본을 자동 삭제하지 않는다. 사용자 프로젝트의 `packageManager`, lockfile, store와 다른 패키지 설정도 변경하지 않는다.

`pnpm@11`은 Homebrew의 keg-only formula다. 설치 성공만으로 일반 `pnpm` 명령의 전환이 끝나지는 않는다. [Homebrew formula](https://formulae.brew.sh/formula/pnpm@11)

## 1. 변경 없이 진단

대상 Mac에서 저장소의 실제 경로를 사용한다.

```zsh
UPDATE_DIR="$HOME/projects/mac-env/shell-update"
zsh "$UPDATE_DIR/migrate-pnpm.zsh"
```

기본 진단은 기존 `pnpm` 실행파일을 실행하지 않는다. Corepack이나 프로젝트 버전 선택이 진단 중 다운로드를 시작하는 일을 피하기 위해 실행 경로와 Homebrew 정보를 조사한다. 셸 설정, 백업, 패키지를 변경하지 않는다.

진단 결과에서 다음을 확인한다.

- 선택된 Homebrew와 목표 formula, 설치 상태
- 현재 PATH에서 발견한 pnpm·pnpx와 확인 가능한 충돌
- `${ZDOTDIR:-$HOME}/.zshrc` 및 심볼릭 링크가 가리키는 실제 수정 대상
- 이미 적용된 관리 블록 유무와 변경 계획

진단의 종료 코드 `0`은 조사 완료를 뜻하며, 설치나 사용자 셸 전환 완료를 뜻하지 않는다. 별도 자식 zsh에서 실행하는 도구는 호출자 셸의 모든 동적 alias·function을 볼 수 없다. 사용자 초기화 파일을 진단 목적으로 자동 실행하지도 않는다.

## 2. Node.js가 없는 첫 환경

Homebrew와 Homebrew로 설치한 nvm은 기존 실행 전제다. 이 도구는 두 프로그램 자체를 설치하는 bootstrap을 제공하지 않는다.

Homebrew bottle 제공 범위는 macOS 버전과 CPU에 따라 다르다. Intel Mac 등 bottle이 없는 조합에서는 소스 빌드와 추가 빌드 의존성(Node 포함) 설치가 필요할 수 있다. 모의 테스트는 해당 기기의 실제 설치를 검증하지 않으므로, 담당 에이전트가 설치 계획과 결과를 별도로 확인한다. [pnpm@11 지원 범위와 빌드 의존성](https://formulae.brew.sh/formula/pnpm@11)

Node.js 24가 아직 없다면 먼저 기존 업데이트 루틴으로 준비한다. 이 단계도 실제 패키지를 변경하므로 해당 Mac에 대한 승인 후 수행한다.

```zsh
zsh "$UPDATE_DIR/update.sh" --auto
```

Node.js 준비가 끝난 뒤 pnpm 미설치 안내로 실패할 수 있다. 이 경우 전체 업데이트가 완료된 것은 아니다. nvm이 초기화된 사용자 셸에서 `nvm use 24`로 활성화하고, 다음 전환 절차를 진행한다. nvm 초기화 자체가 실패했다면 해당 오류부터 해결한다.

`migrate-pnpm.zsh`에는 별도의 Node.js 설치 로직을 추가하지 않는다.

## 3. 승인 후 적용

담당 에이전트는 진단 결과를 근거로 **대상 Mac의 Homebrew pnpm 설치·갱신과 표시된 셸 설정 파일 변경**에 대한 승인을 확인한다. 새 메이저 전환, 다른 패키지 제거, 추가 초기화 파일 수정은 이 범위에 포함되지 않는다.

```zsh
zsh "$UPDATE_DIR/migrate-pnpm.zsh" --apply
```

적용은 목표 formula를 확보하고 프로젝트 밖에서 해당 절대경로 실행파일의 메이저를 검증한 뒤, zsh 설정의 관리 블록을 반영한다. 설정 변경 전 원문을 백업하며, 이미 같은 상태이면 블록과 백업을 계속 추가하지 않는다. `.zshrc`가 심볼릭 링크라면 실제 대상 파일을 변경하고 링크 자체는 보존한다.

관리 블록은 목표 Homebrew `opt/bin`을 PATH에 추가하고, `pnpm`·`pnpx` 함수를 목표 실행파일로 연결한다. 함수 호출 시에도 해당 경로를 PATH 앞에 두어 하위 명령에 전달한다. 따라서 nvm이 PATH를 다시 정렬해도 일반 대화형 zsh의 pnpm 호출은 목표 경로를 사용한다.

확인 가능한 기존 동명 alias·function이나 비정상 관리 블록이 충돌하면 임의로 덮어쓰지 않고 중단한다. 적용 명령의 성공이 현재 열려 있는 부모 셸의 변경을 의미하지는 않는다. 새 터미널을 열어 다음 검증을 수행한다.

## 4. 완료 확인

새 zsh에서, 사용자 프로젝트 밖에서 확인한다.

```zsh
whence -va pnpm pnpx
(cd / && pnpm --version)
nvm use 24
whence -va pnpm pnpx
(cd / && pnpm --version)
```

완료 기준은 다음과 같다.

1. 일반 pnpm·pnpx 호출이 관리 블록의 함수를 거쳐 목표 Homebrew 실행파일로 연결된다.
2. 프로젝트 밖 pnpm 버전이 승인된 메이저이며, nvm 전환 뒤에도 같다.
3. `migrate-pnpm.zsh --apply`를 반복해도 관리 블록이 중복되지 않는다.
4. `update.sh --auto` 재실행이 성공하고, 목표 계열의 갱신 결과를 확인할 수 있다.

함수는 `command pnpm`, 함수 정의를 읽지 않는 다른 셸, 독립 실행된 프로그램의 PATH 탐색을 모두 강제하지 않는다. 기존 npm·Corepack shim, 동적 셸 정의가 있는 Mac에서는 담당 에이전트가 실제 사용 경로도 따로 검증한다. 우회 경로가 다른 pnpm을 실행한다면 해당 경로까지 전환 완료했다고 보고하지 않는다. 프로젝트가 별도로 지정한 패키지 관리자 정책은 이 절차로 수정하지 않는다.

## 5. 실패·복구·반복 실행

| 상태 | 처리 |
| --- | --- |
| 목표 formula 미설치 | 전환 도구의 진단 후 승인된 `--apply`로 설치한다. |
| 목표 formula가 pin됨 | 최신 갱신을 완료했다고 보고하지 않는다. pin 해제가 승인 범위에 포함되는지 확인한다. |
| 설치 또는 실행 검증 실패 | 성공으로 표시하지 않는다. 출력된 실패 원인을 해결한 뒤 재실행한다. |
| 셸 설정 충돌·쓰기 실패 | 해당 파일과 충돌 정의를 확인한다. 다른 사용자 설정을 삭제하거나 전체 파일을 덮어쓰지 않는다. |
| 적용 후 셸 설정 복구 필요 | 출력된 원본 백업과 복구 경로를 확인하고 아래 절차를 따른다. |

원문 백업은 실제 설정 파일과 같은 디렉터리의 `<설정파일>.shell-update-pnpm.XXXXXX` 형태로 보관한다. 실제 파일명과 복구 명령은 적용 결과에 출력된다.

설정 복구는 현재 파일과 백업을 먼저 비교한다. 적용 이후 사용자가 설정을 추가했다면 백업 전체를 덮어씌우지 않고 관리 블록만 되돌린다. 복구할 변경 범위를 승인받은 뒤 출력된 경로를 사용한다. 설정 복구가 Homebrew 패키지를 이전 버전으로 되돌리는 것은 아니며, 기존 설치본 자동 삭제나 패키지 전체 rollback은 제공하지 않는다.

승인된 메이저를 바꿀 때는 `pnpm-policy.zsh`를 변경하고 각 Mac에서 진단·승인·적용·새 셸 검증을 다시 수행한다. 저장소 정책만 바꾼 상태를 모든 Mac의 전환 완료로 간주하지 않는다.

## 다른 Mac 담당 에이전트에게 전달할 요청

> 이 저장소의 `docs/pnpm-migration.md`에 따라 현재 Mac을 먼저 읽기 전용으로 진단해 주세요. 실제 저장소 경로, Homebrew와 Node.js 상태, 수정할 셸 설정 대상, 기존 pnpm 충돌과 필요한 변경을 보고해 주세요. 패키지 설치·갱신과 셸 설정 변경은 해당 Mac에 대한 승인을 받은 뒤 `migrate-pnpm.zsh --apply`로 진행하세요. 새 zsh와 nvm 전환 뒤의 실행 경로·버전, 반복 실행, `update.sh --auto` 결과를 확인하고 수행한 검증과 남은 우회 경로를 구분해 보고하세요. 프로젝트의 packageManager·lockfile·store와 기존 다른 패키지는 변경하지 마세요.
